## 🎮 함수 포인터 디스패처 (Function Pointer Dispatchers)

게임 전체에 **간접 점프 테이블** 패턴이 사용되고 있습니다:

### 1. FUN_1000_0e30 - 객체 상태 디스패처
```c
(*(code *)*(undefined2 *)(*(byte *)0x1691 + 0xe3f))();
```
- **주소 계산**: `0x1691` 값 + `0xe3f` 오프셋
- **용도**: 객체 타입/상태별 다른 함수 호출
- **호출자**: 메인 루프의 FUN_1000_0360

### 2. FUN_1000_16e0 - 다른 객체 디스패처
```c
(*(code *)*(undefined2 *)(*(byte *)0x168f + 0x16ef))();
```
- **주소 계산**: `0x168f` 값 + `0x16ef` 오프셋
- **용도**: 객체 처리 (타입별)

### 3. FUN_1000_48e0 - 스프라이트 렌더링 디스패처
```c
(*(code *)*(undefined2 *)0x18c6)();
```
- **주소**: `0x18c6` (고정 주소)
- **용도**: 스프라이트 타입별 렌더링 함수 호출
- **호출자**: FUN_1000_029a (메인 루프)
- **맥락**: `DAT_1988_4664 = sprite_address` 직후 호출

### 4. FUN_1000_599d - 화면 업데이트 디스패처
```c
(*(code *)*(undefined2 *)0x18d8)();
```
- **주소**: `0x18d8` (고정 주소)
- **용도**: VGA 수직 블랭킹 전 호출 (화면 업데이트)
- **호출자**: FUN_1000_3830 (메인 게임 로직)
- **특징**: 2번 연속 호출 후 `in(0x3da)` 대기

**공통 패턴**:
- 게임 상태/객체 타입에 따라 동적으로 함수 전환
- OOP의 가상 함수 테이블(vtable)과 유사한 C 구현
- Ghidra가 "Too many branches" 경고를 표시하는 이유

## 🎯 미발견 함수

### FUN_1000_12c0 ⭐⭐⭐ 최우선 타겟
- **호출자**: FUN_1000_3f71
- **추정 기능**: 스프라이트 Blit (화면에 그리기)
- **문제**: 디컴파일 실패 또는 외부 함수
- **다음 단계**: Ghidra에서 직접 확인 필요

### 룩업 테이블 (FUN_1000_0d64 파라미터)
- **위치**: in_BX 레지스터
- **크기**: 16 bytes
- **용도**: 4-bit 팔레트 변환
- **다음 단계**: FUN_1000_0b94 어셈블리 직접 확인
